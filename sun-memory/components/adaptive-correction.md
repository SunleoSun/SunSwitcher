# Adaptive Correction Runtime

## Purpose

`src/adaptive/adaptive_runtime.rs` connects input/correction with canonical SQLite state without database I/O in the keyboard hot path. It owns the current immutable lexical snapshot, the background DB worker, the correction confidence threshold, learning commands, and adaptive correction sessions.

## Ownership boundary

`AdaptiveLexicalRuntime::start` builds the initial `LexicalSnapshot` from enabled system `LanguagePack`s plus `UserLexicon` and the persisted `IgnoredWords` override set. The runtime owns one minimum correction confidence and gives that same value to typed sessions and clipboard-text learning so admission cannot disagree with automatic correction policy.

The background worker is the adaptive runtime component that mutates `Database`. Successful user-word or ignored-word membership mutations reload the canonical `user_words` + `ignored_words` views and atomically swap the derived lexical snapshot while reusing unchanged language packs. Application feature preferences are separate from lexical snapshot ownership: production reads the live `SettingsStore` and passes a typed `CorrectionFeaturePolicy` into each session decision.

## Learning contract

Typed learning occurs only for completed tokens whose correction decision is `Keep`. Unknown alphabetic kept tokens are added to `user_words`; exact system words are not duplicated, and normalized spellings present in `ignored_words` are never admitted while that suppression exists. Existing user words are re-observed to advance usage/recency. Successfully applied autocomplete acceptance uses the same typed-token learning command for the lexical words the user chose, so an accepted existing user word advances usage/recency; uncertain or failed insertion does not. Correction history is not a negative vocabulary authority and runtime startup does not reinterpret or clean `user_words`; it simply loads the persisted vocabulary. Learning uses the lexical provider's canonical core rather than the raw deferred token: layout-ambiguous punctuation can be retained temporarily for wrong-layout interpretation but must never become part of a kept user word or rolling sequence, and punctuation-only physical tokens resolve to no lexical word and clear rolling context. The correction session also owns a five-word rolling canonical context for typed multi-word learning. Kept words are appended immediately; applied automatic corrections append the canonical corrected word, stripping rendered punctuation before sequence persistence, but defer that sequence observation while immediate Undo is possible. If Undo succeeds, the canonical restored original replaces the corrected word in the rolling context and is the version written to sequence history. An aborted/uncertain replacement records no sequence evidence and clears the rolling context because visible text is not proven. Intervening input finalizes a non-undone proven correction.

`LearningClient::observe_text` is the clipboard-text learning path. It bounds learning to at most 40 KiB at a UTF-8 boundary and, when that byte cap lands inside a token, drops the partial trailing token rather than learning an arbitrary fragment. It tokenizes that safe prefix once, runs tokens through the same `LexicalCorrectionProvider` + `CorrectionEngine` at the runtime confidence threshold, and admits only `Keep` tokens to `user_words`. Copied tokens that would be corrected are never taught as valid vocabulary; batched user-word persistence preserves one upsert per kept occurrence so repeated copied user words still advance canonical use-count semantics, while the live `UserLexicon` snapshot reloads once after the batch. Near-duplicate copied words that are one edit/transposition from an earlier newly kept clipboard word in the same payload canonicalize to that earlier word instead of being learned as separate vocabulary. Canonical 2-5 word sequence n-grams are also persisted in one batch and the sequence snapshot is reloaded once.

## Hot-path contract

`CorrectionFeaturePolicy` is the single runtime owner of the two user-facing correction switches. Same-layout typo candidates are controlled by `enable_autocorrections`; exact cross-layout replacements are controlled by `enable_auto_keyboard_switches`; a cross-layout candidate that also needs typo repair requires both settings. Live-prefix layout switching is gated by the same auto-keyboard-switch setting. If the live settings snapshot cannot be read, production fails closed with both automatic correction classes disabled. A confirmed ignored-word mutation may immediately re-evaluate either the still-owned current token or an explicit selected spelling against the refreshed lexical snapshot. The current-token path snapshots the token without consuming it, including physical-key metadata needed for layout-ambiguous punctuation, and only emits a live replacement when the canonical correction decision is cross-layout. The selected-text path likewise requires a canonical cross-layout correction before the Windows layer applies the selected replacement; ignore never performs an unconditional layout transform.

Tracked-word Ignore uses the lexical provider canonical core from the still-owned CompletedToken, not the raw visible token. This preserves physical-key evidence while excluding deferred layout punctuation from ignored_words; for example the tracked English-layout jr? physical span suppresses canonical jr, then the refreshed snapshot can re-evaluate the original owned span as Russian ок,.
Correction lookup uses immutable snapshots only. Physical-layout transformation preserves unmapped non-alphabetic characters such as digits while still failing closed on unmapped letters, so learned identifiers such as `AA33` can be reached from the opposite-layout spelling `ФФ33` without assigning a language to the user word. A one-character spelling that exists only because of the immutable system dictionary may still resolve to an exact one-character word under the opposite physical layout; this prevents system letter/abbreviation rows from blocking legitimate short wrong-layout words such as `z` -> `я` or `b` -> `и`. An explicit learned one-character `user_words` row normally remains authoritative and blocks that reinterpretation, but a learned one-character alias can still yield an opposite-layout short Russian function word (`а`, `в`, `и`, `к`, `о`, `с`, `у`) when that target is itself a stronger learned user word. This keeps accidentally learned aliases such as `b` from blocking frequent `и`, while a heavily used source letter still wins. A proposed completed-token replacement remains pending until the Windows side-effect owner reports `ReplacementOutcome::Applied`; only then is the correction event persisted. The live application session also runs a pre-boundary live-prefix policy for unfinished tokens: it uses only RAM snapshots, bounded top-3 prefix evidence from word and sequence completion, physical layout transforms, technical-token early exits, and no SQLite/delete-index/edit-distance work on each keydown. Strong live-prefix decisions produce a separate live-prefix replacement action that suppresses the current physical keydown, deletes only the previously visible owned prefix, inserts the corrected prefix, records the correction after `Applied`, refreshes completion from the corrected current prefix, and remains undoable with Pause. Applied live-prefix replacements also set a typed live layout state; the same `LivePrefixLayoutPolicy` is the single owner of typed thresholds, decision trace, forward switching, and reverse hysteresis, while `AdaptiveCorrectionSession` only owns state/effect lifecycle. `LivePrefixThresholds` now has one explicit `reverse_margin` rather than the previous equivalent pair of reverse margin plus current-language bonus. Its calibrated defaults are `min_score=2.0`, `switch_margin=1.7`, `reverse_margin=2.7`, and `layout_penalty_scale=2.0`. The calibration uses 100 exact words from the built-in FST dictionaries (50 English, 50 Russian) with length buckets 10 words of length 4, 32 of length 5-6, 27 of length 7-8, 23 of length 9-11, and 8 of length 12+, plus technical-token controls and controlled EN→RU→EN / RU→EN→RU double-switch cases. The chosen forward margin lies inside the zero-error 1.5-1.8 plateau; the chosen reverse margin lies inside the zero-error/zero-controlled-error 2.4-3.0 plateau, while 3.2+ caused large reverse delays. With the chosen defaults the 100-word corpus has zero false/missed/wrong-target switches, zero false/missed reverses, zero technical false switches, and at most one character of additional switch/reverse delay. Live state is cleared on completed-token boundary, explicit layout-switch ownership, aborted effects, or Pause undo. Certification keeps scorer/corpus calibration in `src/adaptive/live_prefix_certification.rs` and session/effect lifecycle checks in `src/adaptive/adaptive_runtime_certification.rs`, so no second scorer or completion-side layout decision path exists. A wrong-layout candidate carries its typed target `LanguageId` through replacement actions; after and only after the replacement is proven applied, the Windows side-effect owner requests that same foreground keyboard layout so subsequent physical typing continues in the corrected language. Shifted punctuation that has a layout mapping remains part of the wrong-layout correction token. The Windows hook maps both physical digit-7 and OEM slash keys to typed `PhysicalKey` identities, allowing cases like `rfr&` -> `как?` and English-layout `jr?` -> Russian `ок,` to transform punctuation with the same physical span instead of completing the lexical core too early. Same-layout typo corrections carry no target language and never change the OS layout. Completed-token correction also preserves the ordered ASCII-digit signature across candidate generation, preventing learned alphanumeric identifiers with different numeric suffixes from being collapsed by edit-distance correction while retaining same-digit alphabetic typo correction. Intervening input, downstream suppression, stale foreground/revision ownership, or failed injection aborts the pending effect. The keyboard hook never waits on SQLite.

## Undo contract

Automatic replacements are recorded in `correction_events` only after they actually apply. Undo is two-phase: restore text externally first, then commit persistence. A successful commit atomically marks the exact correction event undone, removes a matching ignore override if present, and inserts/updates the restored original in `user_words`. Pause with no current selection requests this immediate Undo. Plain Pause with an existing selection forgets that normalized spelling from both `user_words` and `ignored_words`; Ctrl+Pause with an existing selection adds it to `ignored_words` and removes any matching learned row. The selected-word paths immediately invalidate correction/completion tracking, while the background worker performs persistence, refreshes the filtered lexical snapshot, and returns a typed outcome used by the UI notification. Immediate Undo remains limited to safely reversible character-boundary corrections and is disarmed by intervening input.
