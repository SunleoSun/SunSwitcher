# Autocomplete UI and caret anchoring

## Current boundary

`src/windows/caret_locator.rs` owns discovery of an on-screen text-caret anchor. It returns a typed `CaretAnchor` with screen-space coordinates, caret height, and the backend that produced it. Completion policy and ranking do not belong here.

The current caret discovery order is:

1. UI Automation `TextPattern2::GetCaretRange`; the focused UIA element is tried first, then up to eight raw-view ancestors, then a bounded raw-view descendant search (depth 8 / 128 elements) because browsers, terminals, and composite editors may expose the text provider deeper in the accessibility subtree;
2. UI Automation `TextEditPattern`, converted through its inherited `TextPattern`, with the same focused/ancestor/bounded-descendant discovery;
3. UI Automation text selection, including adjacent-character recovery for degenerate caret ranges;
4. MSAA `OBJID_CARET` + `IAccessible::accLocation`, tried first on the foreground GUI thread's focused HWND and then on the top-level foreground HWND, before classic Win32 caret discovery;
5. Win32 `GetGUIThreadInfo` + `ClientToScreen` for classic caret-owning controls.

`CaretLocator::locate()` remains the preferred anchor path used by the live autocomplete popup. If UIA/MSAA/Win32 cannot expose a caret while suggestions are active, production now uses `fallback_anchor()` as a final fail-soft placement: current pointer first, foreground-window geometry second. That fallback is captured once for the active suggestion session and is not recomputed every frame, so the popup does not chase the mouse; a subsequently discovered real caret immediately takes ownership again.

## Placement

`popup_placement` places the popup below the proven caret with a small gap, clamps it to the nearest monitor work area, and flips above the caret if there is insufficient vertical space below. UIA caret ranges that expose no rectangle are recovered from the adjacent character range so Chromium/Electron-style degenerate carets can still produce screen geometry. Caret discovery and popup placement remain separate behaviors.

## egui popup

`src/windows/autocomplete_popup.rs` owns the runtime suggestion window. It runs a borderless, taskbar-hidden, always-on-top egui/Glow viewport with `active=false` and explicit opaque native composition. The viewport starts hidden and is shown only while suggestions exist; identical state updates do not repaint, and unchanged popup geometry is not resent to the native window. Repaint is event-driven: a changed suggestion/selection state wakes the retained `egui::Context`, identical updates do not repaint, and the popup does not poll UI Automation on a fixed timer while idle. With suggestions, `App::logic` prefers a real caret anchor and otherwise uses the frozen final fallback described above, then resizes and moves the already-live viewport through `popup_placement`. Rendering paints an opaque dark background, selected-row fill, and white text, with matching native clear color. Because this build intentionally uses `eframe` with `default-features = false`, the popup installs a Windows system font at startup (Segoe UI, then Arial/Tahoma fallback) into egui's proportional and monospace families. Without an explicit font definition, egui still paints shapes but text glyphs are absent. Popup startup fails instead of silently showing a textless window if none of the supported Windows fonts can be loaded. Native `mouse_passthrough` is intentionally disabled for this Glow window: winit implements cursor hit-test disabling on Windows with `WS_EX_TRANSPARENT | WS_EX_LAYERED`, and the layered style was observed to expose an unpainted/transparent OpenGL client area instead of the egui frame. The popup therefore prioritizes correct opaque rendering and non-activation at creation over native click-through. The popup owns the single dedicated Windows UI thread and single eframe/winit event loop used by SunSwitcher UI. The clipboard manager is rendered inside that same event loop/viewport instead of creating a second `run_native`, because winit allows only one event loop in this process. `replacement_probe` drives this shared UI runtime from the typed completion session and clipboard hotkeys, and `src/bin/completion_popup_probe.rs` remains the lower-level diagnostic probe that can display caret/fallback source information.

## Input and hotkeys

Live completion normally activates after three characters in the current token. Unmodified Up/Down changes selection; unmodified **Tab** accepts the complete selected suggestion while Enter always passes through to the foreground application; Alt+Right accepts exactly the next word plus its separating space; unmodified Delete removes the selected prediction; and unmodified Esc dismisses. After a proven Alt+Right insertion, completion tracking advances to the accepted word and sequence suggestions refresh immediately. The remainder that was visible in the selected row before acceptance is protected as the prefix of the refreshed top row: ranking may extend it with newly predicted words, but may not change those already-visible words. Repeated Alt+Right therefore never inserts an unseen replacement word; Up/Down deliberately releases that protection and chooses another path. While completion is active, the physical Alt modifier used to form Alt+Right is owned by SunSwitcher: its down/up pair is suppressed from downstream hooks, while the internal keyboard state still records Alt so Right can resolve to `AcceptNextWord`. The accepted word is injected as Unicode only; no synthetic Alt release/repress is sent to the foreground application. Delete removes the row immediately from the current session; learned multi-word rows delete their exact `text_history` source, while single-word candidates persist a completion-only suppression so dictionary/user lexical authority is not destroyed. Keyboard runtime resolves a completion command before calling the downstream hook chain: handled command keydown/up pairs are SunSwitcher-only; only `Pass` from an inactive/non-consuming completion session is forwarded. Double Shift is a separate layout-switch command: two otherwise plain **physical** Shift taps within 400 ms trigger on the second Shift release; SunSwitcher/foreign injected keyboard transitions never participate in the gesture. A freshly owned typed layout span wins first because it is the strongest proof of the text immediately before the caret and avoids UIA/clipboard work; mouse or navigation selection invalidates that ownership before Double Shift. With no owned span, Double Shift first probes for an explicit selection with clipboard-preserving Ctrl+Insert, which is layout-independent and safe even when UI Automation exposes no selection. Shift+navigation, completed mouse-drag selection, and mouse double-click selection are tracked as typed user-selection intent. Existing explicit selections try Ctrl+Insert first, then Ctrl+Shift+C for terminal-style copy bindings; Ctrl+C is allowed only when UIA itself proves the selection, so it is not sent on intent alone. A second safe Ctrl+Insert probe distinguishes a selection that remained active from one that collapsed after copy; retained selections are replaced directly, while collapsed-at-start selections are reconstructed with the captured character count before the same Delete+Unicode replacement. Without an owned span or explicit selection, the previous-text fallback creates one bounded 64-character backward selection with physical Shift+Left instead of relying on application-specific Shift+Home semantics. After the synthetic Shift+Left, a UIA-selected text range wins when available, which avoids browser clipboard normalization or expanded contenteditable copies. Otherwise it tries safe Ctrl+Insert and then Ctrl+Shift+C; Ctrl+C is deliberately not used for this synthetic previous-text probe, so a terminal that refuses copy shortcuts fails closed instead of receiving an interrupt/printable C. If the synthetic backward selection remains active, SunSwitcher leaves that exact active chunk selected and applies the replacement as `leading copied text + transformed target + suffix` in one Delete+Unicode batch instead of collapsing the browser selection and selecting backward again. If copy collapsed the selection to the start, SunSwitcher advances by the captured caret-step count. From that restored original caret, SunSwitcher finds the trailing non-whitespace range (including layout punctuation), moves left across preserved trailing whitespace, selects only the target with Shift+Left, replaces it, and moves right across the preserved whitespace. This keeps capture/replacement relative to the proven original caret and avoids per-character clipboard probing. The owned `InputBuffer` layout span retains punctuation and trailing whitespace through Double Shift, remains owned after a successful transform for repeated switching in the opposite direction, and is replaced through the same Backspace+Unicode effect path used by automatic correction. Once ownership is unavailable, clipboard capture is used only after SunSwitcher has evidence of an explicit selection from UIA, keyboard Shift+navigation, mouse-drag, or mouse double-click selection intent, or has itself created the bounded Shift+Left backward selection. The selected/previous text transform returns both transformed text and target language. Captured selections that remain active are replaced by one contiguous Delete+Unicode batch; terminal selections that collapse on copy are reconstructed from the proven caret anchor with Shift+Right before that same replacement. The previous-text fallback either replaces the retained active backward chunk directly or reconstructs the trailing non-whitespace range relative to the restored original caret via Left trailing offset, Shift+Left target selection, replacement, and Right trailing-whitespace restoration; line-start normalization and Ctrl+word-navigation are not used. Only after the text effect succeeds does SunSwitcher request the matching installed foreground keyboard layout through `WM_INPUTLANGCHANGEREQUEST`, so the next physical keystroke uses the same language as the converted text. Double Shift diagnostics use the `[double-shift]` stderr prefix and report tracked-span invalidation from mouse/navigation input, the chosen capture path, UIA observations before/after copy, clipboard source/range counts, and the final replacement path; the diagnostics describe observed state and never branch on application identity. The Double Shift editing effect is deferred from the second physical Shift key-up hook callback onto the hook thread message queue: the low-level hook never performs the multi-step SendInput/clipboard capture synchronously, so injected selection/copy events are processed only after the hook returns and Windows finishes the physical Shift release; a still-held physical Shift at deferred dispatch fails closed instead of editing under ambiguous modifier state. Backward chunk capture may include CRLF when the bounded selection crosses a line boundary; caret restoration treats each CRLF pair as one navigation step and still derives only the trailing non-whitespace target at the original caret. Synthetic text-range selection uses physical left Shift with extended Left/Right navigation rather than generic VK_SHIFT or line-start shortcuts; navigation-cluster keys keep the Windows extended-key identity. Safe probing uses physical left Control plus extended Insert (Ctrl+Insert); Ctrl+Shift+C is the terminal-style safe fallback; Ctrl+C is reserved for UIA-proven existing selections only, so neither unknown explicit-selection probing nor synthetic previous-text probing can degrade into terminal interrupt/printable C/С behavior. Any explicit input invalidation clears layout-span ownership even when that span came from a previous Double Shift replacement; navigation therefore cannot leave a stale transformed span eligible for a later gesture. A tracked span that exists but has no layout transform is dropped and Double Shift continues into the normal capture fallback instead of ending the gesture. Clipboard manager defaults are handled by the same Windows keyboard runtime: Ctrl+Shift+Num- opens the text history window on the Current tab, and Ctrl+Shift+Num+ opens it on the Pinned tab. The manager stores the foreground window captured at hotkey time, switches the shared SunSwitcher UI viewport into a clipboard-history mode with Current/Pinned tabs, case-insensitive filter, top-row numeric insert buttons, Pin/Unpin controls, and a settings view listing the current default hotkeys. Text entries are inserted back into the captured foreground window via Unicode `SendInput`, then marked used in SQLite so Current order moves up without changing Pinned order. These bindings are defaults only; persistent configurability belongs to the future settings UI.

## Clipboard manager window

The clipboard manager uses the shared SunSwitcher egui viewport, but when history is visible it switches that viewport into a normal movable/resizable decorated window (`Decorations(true)`, `Resizable(true)`, explicit on-screen position, and focus). Closing the native window, pressing Escape, or pressing the in-window close button hides the manager back to tray instead of shutting down the process. A persistent Win32 tray icon is created on a separate message-window thread through `Shell_NotifyIconW`; clicking it opens the Current clipboard tab. Clipboard rows use a light high-contrast theme, Current/Pinned tabs remain at the top, the case-insensitive filter and Settings button live on the bottom row, and number keys 1-9 insert the corresponding visible row when a text edit is not focused.
