# Completion

## Ownership

`src/completion/` owns completion lookup and ranking. `CompletionProvider` consumes immutable runtime state only: the current lexical snapshot for system/user word completion, the current sequence snapshot for multi-word completion, and the current completion-word suppression snapshot. Completion lookup never queries SQLite. `SequenceHistory` interns normalized tokens once and stores compact 32-bit token-ID sequences plus RAM-only next-token/context posting indexes; each interned normalized token is one shared `Arc<str>` used by both ordered prefix lookup and ID-to-token resolution, context keys keep at most four token IDs inline, and one-entry postings avoid separate heap vectors. Persisted phrase text and normalized token text are therefore not duplicated across indexes. `SequenceSnapshot` keeps that immutable base plus a small immutable overlay of rows updated by learning; overlay rows shadow stale base rows and preserve the same ranking semantics. Per-key sequence evidence therefore narrows to matching indexed candidates without scanning persisted `text_history`.

## Canonical sequence history

Clipboard text observation reuses the same lexical correction decision used for vocabulary admission over a bounded 40 KiB prefix. Each observed token contributes its kept spelling or the confident correction replacement to the canonical token stream; near-duplicate newly-kept clipboard words within the same payload canonicalize to the earlier kept spelling instead of adding a second learned typo. Raw spellings that the corrector would replace are therefore not prediction targets. The canonical stream is expanded into contiguous 2-5 word n-grams and persisted as whole canonical strings in `text_history` in one batch. SQLite retains the complete history; runtime sequence indexing is a bounded derived view so persistent evidence is not destroyed merely to control RAM. A base rehydrate keeps up to 225,000 repeated rows ordered by use count then recency plus the 25,000 freshest singleton rows. This selection follows the existing ranking semantics: repetition dominates the bounded recency term, while singletons differ only by recency. Normal learning applies SQLite `RETURNING` rows directly to the sequence overlay instead of rereading/rebuilding all history; after 1024 distinct touched rows the runtime performs one bounded rebase from that active SQLite view. Explicit multi-word prediction deletion also rebases because membership changed. `text_history.use_count` increases only because that canonical n-gram is observed again; correction itself adds no bonus. Physical typing and proven completion acceptance feed the same `text_history`: `AdaptiveCorrectionSession` owns a rolling context of the last five proven typed words, while `AdaptiveCompletionSession` records the accepted word together with the current completion context; both emit only suffix n-grams ending at each newly resolved or accepted word, so older n-grams are not counted again on every keystroke. Completion receives the same resolved canonical word from the correction session, so a kept or corrected token whose physical layout key deferred punctuation (for example `hello,`) contributes `hello` to completion context rather than a second raw interpretation. Punctuation-only tokens clear context. An applied automatic correction enters the rolling context as the canonical corrected word but its sequence observation is deferred while immediate Undo is still possible; a successful Undo replaces that last rolling word with the canonical restored original before the sequence is persisted. Aborted or uncertain replacement effects contribute no sequence evidence.

Physical typing and applied completion acceptance intentionally have different session-state producers but one learning/persistence behavior path: both submit lexical observations through `LearningClient::observe_typed_token` and sequence observations through `LearningClient::observe_typed_sequence`; the adaptive worker is the sole runtime owner that calls `observe_user_word` / `observe_typed_sequence`, and all typed sequence writes converge on `persist_sequence_observations` -> `Database::record_text_history_batch`. `Database::record_user_word` and `record_user_words_batch` likewise share the same `upsert_user_word`, while single/batch text-history writes share `upsert_text_history`. Session code may derive the current canonical context, but it does not own alternate SQLite learning semantics.

## Multi-word ranking

Context specificity is a separate, higher-priority ranking dimension, not part of the numeric user score. Up to the last four completed context words may match a stored sequence prefix. Sequence lookup also applies the current partial-word prefix before truncating candidates, so a phrase can be suggested directly from its first word even when there is no completed context. Candidates sort by matched context-word count descending, then by user score descending; equal evidence prefers the longer remaining continuation, then deterministic text order. Sequence lookup has one canonical prefix-driven ranking path. With a visible prefix it may deliberately use a less-specific repeated context when the most-specific match would collapse a learned sequence to one displayed word; it prefers the most-specific match that still exposes at least a two-word continuation, falling back to the ordinary most-specific match when none exists. Without a prefix, ordinary context specificity wins. Alt+Right does not select another provider or ranking mode: while the physical prefix is temporarily empty after accepting a word, `CompletionSession` feeds the first already-visible protected continuation word back as the logical lookup prefix. Candidate generation/ranking is therefore the same code path used for manual typing; only session lifecycle owns the source of the prefix. This keeps evidence such as repeated `AA33 AA33` visible without a second completion behavior.

For an entry with `repeat_count = use_count - 1`, the current user score is:

`4 * ln(1 + repeat_count) + exp(-age_days / 14)`

Repetition is intentionally the dominant evidence; recency is a bounded secondary signal. A first observation has no repetition component.

## Word completion

Word completion merges learned `UserLexicon` prefix matches with system `LanguagePack` prefix matches. Prefix lookup and deduplication are normalized/case-insensitive. The current word policy keeps learned user words ahead of system rows; learned words preserve their existing recency/use-count ordering and system rows preserve dictionary-frequency ordering. Suggestion rendering preserves the exact prefix casing already typed by the user. Uniform lower/upper/title words adapt the untyped remainder to that observed case, while mixed/camel identifiers retain their canonical internal casing after the typed prefix. A separate immutable `CompletionWordSuppressions` snapshot filters words that the user removed from autocomplete with Delete. This is intentionally completion-only: hiding `hello` does not delete the system dictionary row or a learned `user_words` row, so spell/correction authority remains canonical and independent from UI preference. The provider widens the pre-filter lookup by the suppression count before final truncation so hidden words do not unnecessarily reduce visible result count. `CompletionSession` is the single owner that merges lexical and sequence suggestions for the popup: sequence evidence remains first, but on a fresh prefix with no completed context it reserves up to half of the popup for lexical word matches so dense phrase history cannot starve learned words such as `sun1`, `sun2`, and `sun3` from the shared prefix `sun`.

## Runtime refresh and live session

`AdaptiveLexicalRuntime` owns the background persistence path. Routine sequence mutations update the bounded immutable overlay from rows returned by SQLite and only periodically rebase the compact base snapshot; completion-suppression membership changes still rebuild their small snapshot. It exposes `completion_provider()` as the typed RAM-only lookup boundary. `CompletionProvider::prefix_evidence` is the bounded scoring API used by live-prefix layout decisions; it inspects capped lexical/sequence evidence without creating full UI suggestions for both layouts, and deliberately ignores completion-only word suppressions so hiding a suggestion cannot change layout/correction authority. Live-prefix trace/certification reads that evidence through the same `LivePrefixLayoutPolicy` decision path rather than a test-only scorer. Completion remains only the bounded evidence provider: `LivePrefixLayoutPolicy` owns switch/reverse/hysteresis decisions and their calibrated thresholds, while `AdaptiveCorrectionSession` owns only the active layout-state lifecycle and application outcomes. User-word changes remain owned by the lexical snapshot store; the provider combines lexical, sequence, and suppression snapshots without SQLite access on keystrokes. Sequence completion is a derived view and may surface only words that are still valid in the current lexical snapshot, so deleting a custom `user_words` term immediately removes its authority once the snapshot refreshes even if historical `text_history` rows containing that term remain stored. Pause-based user-word deletion also invalidates the live completion session and closes the current popup so an already-rendered stale row is not left visible while the background snapshot catches up. Core `CompletionSession` owns the current prefix, up to four completed context words, suggestions, selected index, three-character normal activation threshold, whole-suffix acceptance, one-word continuation acceptance, and the typed deletion target for each row. When Enter or Tab reaches `CompletionSession` as an input boundary, it dismisses the popup and clears completion context even when the current token is already empty; active Tab may instead be consumed by the explicit completion-accept command, while Shift+Enter reaches the ordinary Enter boundary because Shift is not a command modifier in keyboard classification. Delete removes the selected row immediately and records the target locally so an asynchronous snapshot refresh cannot make it flash back into the same session. A multi-word suggestion carries the exact originating `text_history` string even when the displayed completion is context-truncated, so deletion targets the canonical stored row. A single-word suggestion carries normalized `Word(...)` identity and persists completion-only suppression. `AdaptiveCompletionSession` also keeps the lexical words represented by an in-flight Accept/AcceptNextWord command until the Windows effect result arrives; only `Applied` acceptance re-observes those words through normal typed-learning semantics, while `Uncertain` discards the pending evidence. This makes accepted learned-word completions advance their user use-count/recency instead of leaving ranking unchanged. After a proven one-word insertion, the not-yet-accepted remainder that the user already saw becomes a protected prefix of the refreshed top suggestion: ranking may only append after it, so repeated Alt+Right never inserts an unseen replacement word. Correction/layout replacements refresh completion only after the text side effect is confirmed applied. If the replaced text is the current unfinished word, `CompletionSession` replaces its current prefix and reruns the ordinary completion path from the visible replacement. If the word was already completed by a space, the existing last context word is canonicalized in place; no new context word is invented when punctuation/Enter/Tab already cleared sequence context. Successful Undo restores the corresponding prefix or existing context. This lets a wrong-layout correction such as `руддщ ` continue phrase suggestions from canonical `hello` while preserving non-space context boundaries, and lets an explicit Double Shift on an active word immediately refresh suggestions from the switched prefix.

## Validation anchors

- `src/completion/sequence.rs`: context specificity, prefix-filtered sequence lookup, repetition/recency score, longer-continuation tie break, bounded n-gram generation.
- `src/completion/session.rs`: three-character normal trigger, continuation mode, typed context, candidate selection, whole-suffix accept, one-word accept, and protected-prefix extension.
- `src/adaptive/adaptive_runtime_certification.rs`: canonical copied sequence, no correction bonus, repeated sequence wins, first-word phrase prefix completion, stable one-word continuation acceptance, system+user word completion, learned-sequence deletion, system-word completion suppression without lexical deletion, live activation/context completion, Undo-learned completion, plus restart-backed E2E certification that physical typing, full completion acceptance, and next-word acceptance persist exact `user_words`/`text_history` evidence and rehydrate the expected top context prediction; uncertain acceptance certifies both DB and output remain unchanged.
- `src/persistence/database_certification.rs`: text-history repetition survives reopen.
